01 系统架构

排行榜系统分三层：客户端通过 HTTP+Proto2 与 GameServer 通信；GameServer 将请求转换为 gRPC 调用 SocialServer；SocialServer 持有排行榜核心逻辑，数据存于 Redis（热）和 MongoDB（冷）。

02 排行榜类型

RANK_TYPE_ONCE = 1

一次性排行榜：活动有效期内单轮结算。现有业务（balloon / egg / camper_competition）均为此类型。

  • BizId 格式：{bizType}_{actID}
  • 到期后自动结算，或 GM 手动触发
  • 结算后数据永久保留在 MongoDB

RANK_TYPE_PERIODIC = 2

周期排行榜：有效期内按 cycleDays 天数滚动开启多轮，每轮结束自动推进下一轮。

  • BizId 格式：{bizType}_{actID}_r{N}
  • logicalKey（路由键）：{bizType}:{actID} 始终指向当前轮
  • Redis 热数据保留 1 个周期；结算快照保留 2 个周期
  • MongoDB 数据永久保留

06 奖励领取闭环设计

⚠
核心问题：客户端负责发奖，但目前没有调用 ClaimReward 将领取状态写回服务端。rank_claim 表始终为空，导致任何"是否已领"查询均不可信。

正确的领取语义

将 S2SClaimReward（及对应 C-S 消息）设计为原子幂等锁：服务端先写，客户端后发。claimed 的含义改为"调用本次前是否已有记录"： 

// claimed = false → 首次领取，服务端刚写入记录 → 客户端必须执行发奖
// claimed = true  → 之前已有记录（重复调用） → 客户端跳过发奖，避免重复

完整的客户端领取流程

进入排行榜活动入口时
调用 GetRankRounds
获取全部轮次列表及 settled / current 标志
对每个已结算轮次，调用 GetClaimStatus(round=N)
批量查询哪些轮次尚未领取
展示待领取奖励列表
只展示 claimed=false 且用户在奖励名单内的轮次
用户点击领取 → 调用 ClaimReward(round=N)
服务端原子写入；响应 claimed=false 才发奖；claimed=true 说明已领，跳过
✓
服务端 S2SClaimReward 已实现原子写（MongoDB upsert $setOnInsert），多次调用安全幂等。客户端只需保证先调此接口，再执行实际发奖逻辑即可闭环。

08 多节点安全修复

以下 4 项 race condition 已修复，SocialServer 可安全部署多节点（无状态横向扩容）。

领取奖励并发重复（Critical）
原逻辑 GetClaim + SetClaim 非原子——两节点均读到"未领取"后各自写入，导致重复发奖。
修复：store.AtomicClaim 使用 Lua 脚本将 HGET+HSET 合并为 Redis 原子操作，同时处理 null 哨兵； Lua 返回"首次"后再同步查询 MongoDB，应对 Redis 被清空的极端场景，确保全链路幂等。
✓ 已修复
历史轮领取并发重复（Critical）
ClaimHistoricalReward 原逻辑直接 MongoDB GetClaim + SaveClaim，两节点同时读到"未找到"后各自写入。
修复：改用 dao.SaveClaimIfNotExists（$setOnInsert + upsert=true），MongoDB 层原子保证只有一次插入成功。
✓ 已修复
并发分组结算（Critical）
Settle 循环仅以内存 Group.State 为守卫，两节点同时读到 GroupStateOpen 会各自调用 SettleInstance。
修复：在调用 SettleInstance 前通过 store.TryLockSettle(groupID)（Redis SETNX，TTL 10 min）抢占每组结算锁，未抢到的节点直接跳过。
✓ 已修复
PeriodicState 跨节点陈旧（Critical）
syncFromMongo 仅在内存无状态时从 MongoDB 恢复，导致非推进节点的 CurrentRound 永久停留在初始轮次。
修复：改为"若 MongoDB 的 CurrentRound 更大则强制覆盖内存状态"，每次 30 s 同步循环自动追齐最新轮次。
✓ 已修复
机器人 tick N× 倍速增长（High）
所有节点每秒均对同一组机器人执行 tick，积分增长速度等比于节点数。
修复：store.TryLockRobotTick(nowMs)（Redis SETNX，key 含秒级时间戳，TTL 3 s）选出每秒执行节点； 其余节点该秒跳过 tickAllRobots。
✓ 已修复

09 数据存储策略

Redis（热数据）

  • rank:meta:{bizId} — 活动基础信息
  • rank:groups:{bizId} — 分组列表
  • rank:members:{bizId} — 用户→分组映射
  • rank:settled:{instanceId} — 结算快照缓存
    周期：TTL = 2×cycleDays；到期自动失效
  • rank:claims:{bizId} — 领取记录缓存
  • 周期排行榜历史轮热数据在结算后 1×cycleDays 延迟清理（不删 settled / claims）

MongoDB（持久化）

  • rank_config — 活动配置 + PeriodicState（不删）
  • rank_group — 分组数据（不删）
  • rank_member — 用户→分组（不删）
  • rank_score — 积分记录（不删）
  • rank_settled — 结算快照（永久保留）
  • rank_claim — 领取记录（永久保留，幂等依据）
  • rank_inst — 榜单实例元数据（不删）
ℹ
历史玩家回归时，若 Redis 结算缓存已过期，SocialServer 会自动从 MongoDB rank_settled 回填，无需客户端感知。rank_claim 永久保留确保发奖幂等性。
